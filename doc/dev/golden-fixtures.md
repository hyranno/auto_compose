# Golden fixtures

`fixtures/golden/` holds pairs of generator parameters and the tune they produce.
They pin down the exact output of the generators, including the random number sequence.

The fixtures were first generated by the TypeScript implementation, and the Rust port matched
every case. The last commit compatible with TypeScript is 83edec0. Since then the fixtures are
generated by the Rust crate; the TypeScript implementation was removed after ece5a07.
The random numbers come from `rand_pcg::Pcg32`, so the fixtures change if that generator or the
way `rand` turns its output into values changes.

## Layout

```
fixtures/golden/
  tune/<case>.json             {"params": TuneGenerator.Parameters, "expected": TuneSnapshot}
  variant/<case>.json          {"params": VariantGenerator.Parameters, "base": TuneGenerator.Parameters, "expected": TuneSnapshot}
```

`TuneSnapshot` is defined in `crates/auto-composer/src/snapshot.rs`. Times and durations are sums of powers of two,
so the expected values are compared exactly.
`chord[].notenums` is redundant with `root` and `tones` and is there to cross-check the chord computation.

## Usage

- `cargo test` runs `crates/auto-composer/tests/golden.rs`, which regenerates the `tune/` cases with
  `auto_composer::generator::tune::generate` and the `variant/` cases with
  `auto_composer::generator::variant::generate`, and compares them as `TuneSnapshot`.
  The `#[cfg(test)]` modules hold the unit tests.
  Before committing Rust code, run
  `cargo fmt --check && cargo clippy --all-targets --all-features -- -D warnings && cargo test --all-features`
  (`--all-features` also checks `schemas/`, see `schemas.md`).
- `cargo run --example gen_golden` rewrites the `expected` of every case from the current implementation
  and lists the cases that changed. The inputs (`params`, `base`) are kept, so the case files themselves
  define the cases: add a case by writing a file with its inputs (any `expected`) and running the command.
  Regenerate only when a change of output is intended, and review the diff.
  The shared code is `crates/auto-composer/tests/common/mod.rs`.

## Random numbers

Each layer draws from a generator of its own, `random::layer_rng(seed, label)`, with the labels
`cadence`, `chord`, `rhythm`, `pitch` and `variant`. The seed is the seed of the layer if it has one,
or else the seed of the tune (`tune::Parameters::layer_rng`). The label is hashed into the seed, so
layers given the same seed still draw independent sequences, and changing the seed of one layer
changes only that layer and the layers generated from it.

The steps inside a generator (`cadence::generate`, `rhythm::merge_top_branches`, `variant::interpolate`,
...) take a `&mut impl Rng`, so that unit tests can give them specific draws: `ScriptedRng` returns
a fixed list of values in `[0, 1)` (as words that `rand` turns back into those values), and the test
helpers in `generator/mod.rs` return a constant value or count the words drawn.
The variant draws from a single generator through all its steps (`vary_cadence`, `vary_chord`,
`interpolate`, `split_rhythm`, `merge_rhythm`, `toggle_note_on`, ...); `variant::generate_with` takes it.

## Unit tests

The Rust unit tests are in the `#[cfg(test)]` module of each file (`util.rs`, `tune.rs`, `markov.rs`,
`generator/*.rs`, ...). Many were ported from the former TypeScript tests (`src/core/*.test.ts`), whose inputs and expectations are
written as tables for that reason. Values computed in floating point (such as the distributions of
the Markov chain) are compared with a tolerance.
