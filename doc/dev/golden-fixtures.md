# Golden fixtures

`fixtures/golden/` holds pairs of generator parameters and the tune they produce.
They pin down the exact output of the generators, including the random number sequence.
`fixtures/rng.json` pins the raw output of the random number generator itself.

The fixtures were first generated by the TypeScript implementation, and the Rust port matched
every case. The last commit compatible with TypeScript is 83edec0. Since then the known bugs have been
fixed in Rust and the fixtures are generated by the Rust crate; the TypeScript implementation no
longer matches them and its golden test was removed. `rng.json` still comes from reliable-random
(the former `scripts/gen_golden.ts`) and does not change.

## Layout

```
fixtures/rng.json              first u32 outputs of reliable-random for several seeds
fixtures/golden/
  tune/<case>.json             {"params": TuneGenerator.Parameters, "expected": TuneSnapshot}
  variant/<case>.json          {"params": VariantGenerator.Parameters, "base": TuneGenerator.Parameters, "expected": TuneSnapshot}
```

`rng.json` lists `{state, sequence, u32}` cases: `u32` are the first outputs of
`new Random(state, sequence)._random_b()`, and `random()` returns `u32 / 2^32`.
The seeds include negative values and values beyond 32 bits.
reliable-random is a PCG32 variant whose output function differs from the standard one;
`src/core/random.test.ts` contains a reference implementation of the exact algorithm.

`TuneSnapshot` is defined in `crates/auto-composer/src/snapshot.rs`. Times and durations are sums of powers of two,
so the expected values are compared exactly.
`chord[].notenums` is redundant with `root` and `tones` and is there to cross-check the chord computation.

## Usage

- `cargo test` runs `crates/auto-composer/tests/golden.rs`, which regenerates the `tune/` cases with
  `auto_composer::generator::tune::generate` and the `variant/` cases with
  `auto_composer::generator::variant::generate`, and compares them as `TuneSnapshot`.
  `crates/auto-composer/tests/rng.rs` checks `rng.json` against `auto_composer::random::ReliableRandom`,
  and the `#[cfg(test)]` modules hold the unit tests.
  Before committing Rust code, run `cargo fmt --check && cargo clippy --all-targets -- -D warnings && cargo test`.
- `cargo run --example gen_golden` rewrites the `expected` of every case from the current implementation
  and lists the cases that changed. The inputs (`params`, `base`) are kept, so the case files themselves
  define the cases: add a case by writing a file with its inputs (any `expected`) and running the command.
  Regenerate only when a change of output is intended, and review the diff.
  The shared code is `crates/auto-composer/tests/common/mod.rs`.
- `npm test` runs the TypeScript unit tests, including `src/core/random.test.ts`, which checks `rng.json`.
- `scripts/run_ts.mjs` runs a TypeScript file through Vite's module runner,
  because `src/` uses extensionless imports that plain `node` cannot resolve.

## Tracing random number consumption

Each `generate` in `auto_composer::generator` takes a `&dyn RngFactory` and asks it for its own `Rng`
with a label (`cadence`, `chord.root`, `chord.tone`, `rhythm`, `note.pitch`, `variant`).
`ReliableRandomFactory`, the normal factory, mixes a hash of the label into the seed
(`RandomSeed::for_label`), so layers given the same seed (as in the default parameters) still draw
independent sequences. TypeScript used the seed as it is; this is one of the reasons the fixtures
no longer match it.

To see where the draws go, wrap the factory in `RecordingRngFactory`, which writes each draw with its
label to a `RefCell<Vec<RngRecord>>`. (The TypeScript implementation has the same mechanism,
`recordingRngFactory` in `src/core/random.ts`, which was used to bring the port in line.)

`ScriptedRng` returns a fixed list of values, for unit tests that need specific draws (e.g. boundary values).
In Rust, the steps inside a generator (`generate_with`, `generate_roots`, `merge_top_branches`, ...) take a
`&mut impl Rng` for that purpose, and `SharedRngFactory` makes every generator draw from one `Rng`.
The variant draws from a single `Rng` (label `variant`) through all its steps
(`vary_cadence`, `vary_chord`, `interpolate`, `split_rhythm`, `merge_rhythm`, `toggle_note_on`, ...),
which also take a `&mut impl Rng`.

Seeds in the parameter JSON are read as JavaScript does: the number becomes a `f64` and then
`BigInt(x) & U64_MASK`, so integers beyond 2^53 are rounded first and a fraction is an error.

## Unit tests

The Rust unit tests are in the `#[cfg(test)]` module of each file (`util.rs`, `tune.rs`, `markov.rs`,
`generator/*.rs`, ...). Many were ported from `src/core/*.test.ts`, whose inputs and expectations are
written as tables for that reason, and compare exactly where TypeScript printed the value with full
precision. The linear algebra (`linalg.rs`) performs the same operations in the same order as the
JavaScript fallback of vectorious (LU decomposition with partial pivoting), so the Markov chain matched
TypeScript bit for bit.

The TypeScript unit tests describe the TypeScript behaviour, including bugs that the Rust crate has
since fixed (see the git history after 83edec0).
